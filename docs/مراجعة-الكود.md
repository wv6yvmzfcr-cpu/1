# مراجعة كود منصة إيدولينك + لوحة التحكم

هذا المستند يلخّص ما راجعته في الكود الذي أرسلته، الأخطاء التي وجدتها،
وما بنيته لك (لوحة تحكم ويب كاملة + إصلاحات قاعدة البيانات).

---

## 1) الأخطاء التي وجدتها في كودك

### 🔴 خطأ مؤكَّد: عمود `price_verified` غير موجود
في ملف **«٦- الأسعار.sql»** تستخدم العمود `price_verified` داخل عبارات
`UPDATE public.institutes` (في تحديثَي Bright والباقي)، لكنه **لم يُضَف
إطلاقاً** في `ALTER TABLE ... add column` أعلى الملف. نتيجة التنفيذ:

```
ERROR:  column "price_verified" of relation "institutes" does not exist
```

**الإصلاح:** أضفته بأمان في الملف الجديد **«٩- إصلاحات حرجة.sql»**:

```sql
alter table public.institutes
  add column if not exists price_verified boolean not null default false;
```

نفّذ ملف ٨ **قبل** ملف ٦ (أو أضِف السطر أعلى ملف ٦).

### 🔴 نقص جوهري: لا توجد صلاحيات كتابة للمدير (RLS)
فعّلت `row level security` على كل الجداول، لكنك أعطيت **قراءة عامة فقط**
لمحتوى الموقع (المعاهد، الإعلانات، اللغات، العملات، المتطلبات،
أسباب الرفض، مراحل الطلب، الأسئلة الشائعة). لا توجد أي سياسة تسمح
للمدير بالإضافة/التعديل/الحذف على هذه الجداول، ولا بقراءة/إدارة كل
الطلبات والمستندات والملفات الشخصية.

النتيجة: **أي لوحة تحكم ستكون عاجزة عن التعديل** — ستقرأ فقط.
(الاستثناء الوحيد: `partners` و`commissions` و`data_transfers` و`seo_*`
و`blog_posts` لديها سياسات `is_admin()`؛ بقية جداول المحتوى لا.)

**الإصلاح:** ملف **«٩- إصلاحات حرجة.sql»** يضيف سياسات
`is_admin()` كاملة لكل الجداول الناقصة، بشكل إضافي (لا يكسر القراءة
العامة القائمة)، بالإضافة لدالة `am_i_admin()` تستدعيها اللوحة للتحقق.

### 🟡 ملاحظة: احتمال تكرار متطلب MDAC
في **«٣- بطاقة الوصول MDAC.sql»** إدراج المتطلب `mdac` ينتهي بـ
`on conflict do nothing`، لكن جدول `requirements` مفتاحه `id` عشوائي
(`gen_random_uuid`) ولا يوجد قيد تفرّد على `(institute_id, key)`. لذلك
تشغيل الملف مرتين **يُدرج صف mdac مكرراً** بدل تجاهله.

**التوصية:**
```sql
create unique index if not exists requirements_scope_key_idx
  on public.requirements (coalesce(institute_id, '00000000-0000-0000-0000-000000000000'::uuid), key);
```
ثم اجعل الإدراج `on conflict ... do nothing` مستنداً لهذا القيد.

### 🟡 ملاحظة: هشاشة في `src/lib/supabase.ts`
`Constants.expoConfig!.extra` تستخدم `!` (non-null assertion). إن غابت
`extra` (بيئة بناء ناقصة) سينهار التطبيق برسالة غامضة. الأفضل التحقق
وإظهار رسالة واضحة:
```ts
const extra = Constants.expoConfig?.extra;
if (!extra?.supabaseUrl) throw new Error('Missing Supabase config in app.json > extra');
```

### ✅ أشياء جيدة في كودك
- تصميم متعدد اللغات عبر JSONB مرن وذكي (إضافة لغة = مفتاح جديد فقط).
- سياسات RLS لبيانات الطلاب دقيقة (المالك فقط، ومجلد التخزين لكل مستخدم).
- منطق العمولات عبر trigger عند `completed` سليم ومناسب توقيته.
- فصل رأي الذكاء الاصطناعي (`ai_verdict`) عن قرار `status` البشري — ممتاز.

## 2) ما بنيته لك

| الملف | الوصف |
|------|-------|
| `admin/index.html` | لوحة التحكم (واجهة + تنسيق) |
| `admin/schema.js` | تعريف كل الجداول والحقول (محرك موحّد) |
| `admin/app.js` | منطق اللوحة: دخول، صلاحيات، CRUD، تقارير |
| `supabase/٩- إصلاحات حرجة.sql` | إصلاحات أمنية حرجة + صلاحيات المدير + إصلاح `price_verified` |
| `admin/README.md` | دليل التشغيل خطوة بخطوة |

لوحة التحكم **صفحة ويب مستقلة** تعمل بمفتاح `anon` العام فقط (آمن
للمتصفح)، والصلاحيات تُمنح عبر RLS لحسابك المُرقّى كمدير — **دون كشف
مفتاح `service_role` إطلاقاً**.

### تغطية اللوحة
- 📊 لوحة قيادة: إحصائيات + مسار التسجيل (Funnel) + الطلبات شهرياً + أداء الشركاء.
- 🏫 المعاهد، 🏠 الإعلانات/السكن — إضافة/تعديل/حذف كامل بحقول متعددة اللغات.
- 📝 الطلبات: تغيير المرحلة، **مراجعة المستندات** (اعتماد/رفض بسبب مقنّن)، وإضافة أحداث للطالب.
- 📋 المتطلبات، 🚫 أسباب الرفض، 🧭 مراحل الطلب، ❓ الأسئلة الشائعة.
- 🤝 الشركاء، 💰 العمولات (تفويتر/تسديد)، ⚓ مراسي الأسعار.
- 🌍 اللغات، 💱 العملات، ⚙️ إعدادات التطبيق (JSON).
- ✍️ المدونة، 🔎 صفحات SEO، 🔑 كلمات SEO.
- 👤 المستخدمون (عرض).

> **ملاحظة عن النطاق:** طلبك الأساسي كان «لوحة تحكم كاملة كصفحة ويب»
> وهذا ما بنيته واختبرته. لم أُعِد كتابة تطبيق Expo كاملاً (عشرات
> الملفات) لأنه خارج نطاق «صفحة التحكم»؛ لكني أصلحت أخطاء قاعدة
> البيانات التي تمنع اللوحة (والتطبيق) من العمل. أخبرني إن أردت
> إصلاحات إضافية داخل تطبيق Expo نفسه.

## 3) مراجعة ملف «إصلاحاتك الحرجة» (الذي أرسلته)

ملفك كان فكرته الأمنية ممتازة، لكن فيه أخطاء تمنعه من العمل. صحّحتها
كلها في **`supabase/٩- إصلاحات حرجة.sql`** و**اختبرتها فعلياً على
Postgres 16** (بيئة تحاكي مشروعك مع دوال `auth`/`storage` وهمية).

### الأخطاء التي وجدتها وأصلحتها

1. **🔴 عطل قاتل — ترتيب خاطئ:** كنت تعدّل `v_application_pricing`
   (السطر ٢٦) **قبل إنشائه** (السطر ٢٣٨). أثبتُّ عملياً أن الملف
   **يتوقف فوراً** بـ `relation "public.v_application_pricing" does not
   exist` — أي أنه لا ينفّذ **أي** إصلاح. أصلحته بإنشاء الـView أولاً.
2. **🔴 مُشغّل ناقص:** عرّفت دالة `snapshot_quoted_price` لكن **بلا
   `create trigger`** — فلا تُلتقط أسعار العرض إطلاقاً. أضفت المُشغّل.
3. **🟠 توقّف عند اختلاف المخطط:** `alter view v_prices_status …`
   وغيره يتوقف إن لم يوجد الـView. جعلت كل تعديل view محروساً بفحص
   وجوده (`to_regclass`) فلا ينهار الملف.
4. **🟠 حذف مفتاح أجنبي بالاسم المفترض:** `drop constraint if exists
   commissions_application_id_fkey` قد **يفشل بصمت** إن كان اسم القيد
   مختلفاً، فيبقى `on delete cascade` ويظل الخطر قائماً. الآن أكتشف
   اسم المفتاح فعلياً من كتالوج Postgres.
5. **🟠 أعمدة ناقصة تُسقط المُشغّلات:** الدوال تعتمد أعمدة مثل
   `final_price_myr` و`final_fees` و`offer_issued_at`؛ إن غابت تنهار
   المُشغّلات وقت التنفيذ. أضفتها كلها بأمان (`add column if not exists`).
6. **🟠 ثغرة إدراج (لم يغطها ملفك):** حارسك يمنع الطالب عند **التحديث**
   فقط. لكنه يستطيع **إدراج** طلب مباشرة بـ `status='completed'` أو
   `final_price_myr` مزوّر. أغلقتها في مُشغّل الإدراج.

### إثبات بالاختبار (٩ اختبارات — كلها نجحت ✅)

| الاختبار | النتيجة |
|---------|---------|
| الطالب يضبط `status='completed'` | ⛔ مرفوض `status_change_not_allowed` |
| الطالب ينقل `documents → review` | ✅ مسموح |
| الطالب يحقن `final_price_myr` بالتحديث | ✅ يُعاد لقيمته الأصلية بصمت |
| الطالب يحقن `status/final` بالإدراج | ✅ يُفرض `documents` وتُلغى القيم |
| الطالب يعتمد مستنده بنفسه | ✅ يُفرض `pending` دائماً |
| العمولة تُحسب على السعر النهائي | ✅ `1000` لا `price_myr×weeks` |
| حذف الطلب يمحو العمولة | ✅ العمولة تبقى (لا cascade) |
| طالبان في `v_review_queue` | ✅ كلٌّ يرى صفّه فقط، والمدير يرى الكل |
| `delete_current_user` | ✅ يحذف ملفات التخزين + الحساب |
| كل الـViews `security_invoker=on` | ✅ مؤكَّد |
| تنفيذ الملف مرتين (idempotent) | ✅ ينجح بلا أخطاء |

## 4) مراجعة دوال الحافة (Edge Functions)

راجعت الدوال الخمس. التفاصيل ونموذج الأمان في
[`supabase/functions/README.md`](../supabase/functions/README.md).

### 🔴 الخلل المعماري الأخطر: دوال بصلاحيات الخادم بلا تفويض
`partner-deliver` و`doc-review` تعملان بمفتاح `service_role` لكن **بلا أي
تحقق من هوية المُستدعي**. بوابة Supabase تكتفي بوجود أي JWT صالح، ومفتاح
`anon` يُشحن داخل التطبيق (عملياً عام). النتيجة قبل الإصلاح:

- **`partner-deliver`:** أي مستخدم مسجّل يقدر يُطلق تسليم مستندات طالب
  (روابط الجواز/الشهادة + الاسم والهاتف والدولة) إلى webhook الشريك، لأي
  طلب فيه موافقة — تسريب في قلب نظام مشاركة البيانات نفسه.
- **`doc-review`:** أي أحد يشغّل استدعاءات Claude المدفوعة على أي مستند
  ويستخرج بياناته (تاريخ انتهاء الجواز مثلاً).

**الإصلاح (معماري، متقاطع):** طبقة تفويض موحّدة `_shared/auth.ts`:
`requireAdmin` (مدير فقط) و`requireAdminOrService` (مدير أو سرّ داخلي
`X-EduLink-Invoke` لـ Database Webhooks، بمقارنة ثابتة الزمن). لا تعمل أي
دالة بـ `service_role` قبل المرور بها.

### 🟡 إصلاحات أخرى
- **partner-deliver:** يرفض التسليم بلا `webhook_secret` فعلي (توقيع بلا
  معنى)، يتطلّب مستنداً معتمداً واحداً على الأقل، ويسجّل فشل الشبكة بدل
  الانهيار.
- **doc-review:** فشل آمن — إن أعاد النموذج JSON فاسداً تُسجَّل النتيجة
  `review` (مراجعة بشرية) بدل انهيار الدالة.

### ✅ دوال سليمة (أُبقيت كما هي)
- `assistant` و`photo-passport`: تستخدمان توكن المستخدم نفسه فيحصرهما RLS
  في بياناته — تصميم صحيح.
- `seo-generate`: تتحقق `is_admin()` أصلاً قبل استخدام `service_role`.

> **تحفّظ:** لم أستطع تنفيذ `deno check` (Deno غير متوفر في بيئتي)، فراجعت
> الدوال يدوياً بعناية. جرّبها محلياً بـ `supabase functions serve` قبل
> النشر.
